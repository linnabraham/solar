## Terminology Clarification

**Important distinction:**

- **Stage** (DVC concept): Defined in `dvc.yaml`. A pipeline task with:
  - `cmd`: Command to execute (often runs a Python module)
  - `deps`: Input dependencies
  - `outs`: Output artifacts
  - `cache`: Whether to cache outputs

- **Script** (Implementation): The Python file/module executed by the stage
  - Example: `src/torch/vit/predictions_analyze.py`
  - One stage runs one script (primary)
  - Script may depend on utility modules

**Relationship:**
```
Stage: prediction-plots
  ↓ (defined in dvc.yaml)
  ├─ cmd: python -m src.torch.vit.predictions_analyze
  |    ↓
  └─→ Script: src/torch/vit/predictions_analyze.py
         ↓
         Code Docs: docs/code/predictions_analyze.md
         
  └─ outs: plots/predictions/{id}/goes_with_predictions.png
       ↓
       Stage Docs: docs/stages/prediction-plots.md
```

## Approach B Implementation: Cross-Referenced Split

### Architecture

**Two documentation views, linked bidirectionally:**

```
docs/
├── stages/                      # Pipeline view (WHAT gets produced)
│   ├── prediction-plots.md      # Shows: outputs, dependencies, cache behavior
│   ├── xgb-feat-importance.md
│   └── ...                      # Links to → code/predictions_analyze.md
│
└── code/                        # Implementation view (HOW it works)
    ├── predictions_analyze.md   # Shows: docstrings, functions, parameters
    ├── xgb_feat_importance.md
    └── ...                      # Links to → stages/prediction-plots.md
```

**When viewing pipeline-plots stage:**
1. User sees command, inputs, outputs in `docs/stages/prediction-plots.md`
2. Clicks "Implementation" link
3. Now viewing `docs/code/predictions_analyze.md`
4. Sees docstrings, function signatures, parameters

6. Clicks back to stage page or explores related code

1. Developer sees docstrings, functions in code doc
2. Clicks "Generated by stage" link
3. Now viewing stage page with inputs, outputs, cache behavior
4. Understands full pipeline context
